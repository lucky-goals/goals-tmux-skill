# Private file dispatch

Use a private decision file for every initial task and for long, multiline, or conditional instructions. The file carries the complete goal, working directory, constraints, and acceptance criteria. The terminal receives only a short instruction with its path and unique dispatch ID. This keeps large instructions out of terminal input and makes the submitted work identifiable.

## Send and verify

1. Confirm the task is active, the intended pane is a ready Coding CLI, and its current task/coordinator/generation/revision still match the registry. Before dispatching, the runtime evaluates `tui`, `tui_evidence`, and an independent `pane_capture` for the target pane. By default (`tui.require_visible=false`), GUI visibility verification on input/dispatch is advisory: when desktop visibility proof is absent, the runtime records `tui_evidence` with `"advisory": true` and allows the input/dispatch to proceed. When `tui.require_visible=true` is configured (`scripts/tmuxctl config set tui.require_visible true`), require `tui.status=attached`, a non-empty `tui.viewer_gui_session_id`, fresh GUI identity/visibility evidence with `tui_evidence.status=verified`, and `pane_capture` before dispatching. Pane capture is terminal-buffer evidence only; it cannot prove a GUI window is visible. In `iterm2-native` mode, the proof must identify the mapped task pane, not just the outer Control Mode gateway. Read enough screen/history to distinguish a CLI prompt from a shell, a running command, or a menu.
2. Call `invoke` with `operation: "dispatch"`, a new request ID, the exact pane target and fresh observation, current task context, and the full `arguments.instructions` text (multiline is supported). The runner writes an immutable private decision file, records a dispatch ID and CLI round, then sends the generated one-line file instruction. This operation does **not** submit the prompt.
3. Read the pane again. Check that the complete short instruction and dispatch ID are present in the intended CLI input, with no prompt truncation, substitution, or unrelated text. Only then invoke `submit_dispatch` using the same dispatch ID and `input_verified: true`; submission is a separate operation and sends Enter. The runner rechecks `tui_evidence` before sending input (advisory by default with `tui.require_visible=false`, or strict refusal with `TUI_REQUIRED` when `tui.require_visible=true`); if it returns `TUI_REQUIRED`, do not retry the input directly.
4. Observe the CLI identify the dispatch ID and summarize the key constraints, then look for independent evidence that it read and acted on the file. Record that evidence with `task observe-dispatch --task-id TASK --dispatch-id ID --evidence '...'`. A submitted prompt is not the same as a file-read acknowledgement or completed work.
5. Continue with the inline monitor in [monitoring.md](monitoring.md). Do not prepare another dispatch to that pane until the earlier one is observed.

The runtime creates the decision file under private state `dispatches/TASK/` with restrictive permissions and a content digest. Treat it as immutable. Do not move it into the project or put credentials, tokens, or unnecessary private data in it. If an instruction changes before submission, reconcile the reserved dispatch and use the runner's legal state transition; do not silently replace the file.

## Uncertain input

If the input result, screen, or Enter acknowledgement is uncertain, preserve the existing dispatch ID and CLI round. Query `operation-status`, `task show`, and fresh screen/history. Record what is known. Do not resend the file path, press Enter again, or create another dispatch until read-only evidence establishes the previous state. A timed-out call or missing acknowledgement does not mean the CLI received nothing.

If the target is a shell, an unexpected menu, copy mode, or an input-broadcasting pane, stop before submitting and report the actual blocker. When `tui.require_visible=true` is enabled and GUI proof is missing or unsupported, inspect `remediation` first: the runtime already makes one `show_tui` attempt on its initial failure, and that attempt must not be duplicated. For a legacy or external result without a recorded attempt, call `show_tui` once for the existing session and verify again. If proof still fails under strict gating, stop without dispatching; restore advisory mode only if appropriate via `scripts/tmuxctl config set tui.require_visible false`. Do not set `tui.enabled=false` to work around the failure. Headless operation is allowed only when the user explicitly authorized `tui.enabled=false`. Never paste a large task body into an interactive prompt as a fallback.
